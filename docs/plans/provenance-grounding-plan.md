## Problem Statement

A spot-check of `concept-91bcd2b57765` (SLUB Allocator) revealed that its source URL (`Documentation/mm/slab.rst`) is an 11-line stub containing only `kernel-doc` directives. The evidence excerpt claims the document "describes the default slab allocator's design including per-CPU freelists, partial slab lists, cache merging, and SLUB debugging facilities" — none of which appears in the actual document. The concept data, evidence excerpt, and code examples were all generated from model training knowledge, not from the source document content.

This is a systemic issue affecting potentially all 47 source-evidence-concept chains in the database.

### Evidence Excerpt Problem

43 of 47 evidence excerpts were generated synthetically by the model in `scripts/populate_excerpts_and_code.py` (line 19-65). These excerpts describe what the source document *should* contain based on model knowledge, not what it *actually* contains. For stub documents, the excerpts are entirely fabricated provenance.

Only 4 evidence nodes have real excerpts from fetched files stored in `data/sources/`:
- `ev-b01c5353e809` ← `data/sources/rcu_whatisRCU.txt`
- `ev-159c0f56c081` ← `data/sources/locking_spinlocks.txt`
- `ev-693fd54d9af4` ← `data/sources/scheduler_cfs.txt`
- `ev-1e83fb7dcf49` ← `data/sources/mm_page_tables.txt`

### Code Example source_url Problem

22 code examples across 20 concepts have `source_url` attributes pointing to source documents. The code examples themselves are model-generated (they demonstrate correct kernel API usage but are not copied from the source documents). The `source_url` is meant as attribution ("this API is documented here") but when the URL points to a stub, even the attribution is misleading.

---

## Goals

1. **Validate all 47 source URLs** — classify each as substantive, stub, directory, or unreachable
2. **Replace non-substantive source URLs** — resolve stubs to the actual content sources (the C files referenced by kernel-doc directives); resolve directories to the most relevant specific document
3. **Ground evidence excerpts** — replace synthetic excerpts with summaries derived from actual fetched document content
4. **Validate code example attribution** — ensure `source_url` on code examples points to documents that contain or define the demonstrated API
5. **Add pipeline safeguards** — prevent future ingestion from creating ungrounded evidence

## Phase 1: Source Content Validation Tool

### Task 1.1 — Spec DAG mutations

#### `ALG-KK-VALIDATE-SOURCE-CONTENT`
```
kind: algorithm
id: ALG-KK-VALIDATE-SOURCE-CONTENT
language: py
description: Fetches each Source node's URL via HTTP, classifies content as substantive (>100 words prose/code comments), stub (kernel-doc directives only, <50 words of prose), directory (tree listing), or unreachable. For stubs, parses kernel-doc directives to extract referenced C source file paths and builds replacement URLs. Outputs a structured validation report.
preconditionNL: Source nodes exist in the database with url attributes.
postconditionNL: Each source has a classification (substantive|stub|directory|unreachable) and, for non-substantive sources, a suggested replacement URL pointing to the actual content source.
runs-at → stage-delivery
contained-by ← SUB-KK-INGEST
```

#### `INV-KK-SOURCE-CONTENT-SUFFICIENT`
```
kind: invariant
id: INV-KK-SOURCE-CONTENT-SUFFICIENT
language: meta
description: A Source node's URL must resolve to a document with substantive content. Stub documents (pure kernel-doc directives with <50 words of prose) and directory listings do not qualify as sources. When a source URL is non-substantive, it must be replaced with the URL of the actual content source (e.g., the C file referenced by a kernel-doc directive).
predicate: forall Source S. fetch(S.url) returns document D where word_count(prose(D)) > 100 OR S.url points to source code file
predicateNL: Every Source node URL resolves to a document with substantive prose content or directly to a source code file.
enforced: {}
checked-at → stage-delivery
contained-by ← SUB-KK-INGEST
```

### Task 1.2 — Implementation: `src/ingest/validate_sources.py`

New module with the following functions:

#### `classify_content(html_text: str) -> ContentClassification`
- Input: raw HTML/text fetched from a URL
- Returns a dataclass: `ContentClassification(classification: str, word_count: int, kernel_doc_refs: list[str], prose_excerpt: str)`
- Classification logic:
  - If the page is a git.kernel.org tree listing (contains `<table class="list">` with file/directory entries): `"directory"`
  - If the page is an RST/HTML doc:
    - Count words of prose (exclude `.. kernel-doc::` directives, code blocks, and formatting markup)
    - If prose word count < 50 AND has `kernel-doc` directives: `"stub"`
    - If prose word count >= 100: `"substantive"`
    - If prose word count 50-99: `"thin"` (borderline, needs manual review)
  - If fetch fails (HTTP error, timeout): `"unreachable"`

#### `extract_kernel_doc_refs(rst_text: str) -> list[str]`
- Parses RST for `.. kernel-doc:: <path>` directives
- Returns list of file paths (e.g., `["mm/slub.c", "mm/slab.h"]`)
- These become candidate replacement URLs: `https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/{path}`

#### `resolve_directory_url(dir_url: str) -> list[str]`
- Fetches the directory listing from git.kernel.org
- Returns list of file URLs within the directory
- Filters to `.rst`, `.txt`, and key `.c`/`.h` files
- Used to find the best replacement source for directory-type URLs

#### `build_replacement_url(kernel_path: str) -> str`
- Converts a kernel source path like `mm/slub.c` to the full git.kernel.org blob URL
- Template: `https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/{path}`

#### `validate_all_sources(conn: sqlite3.Connection) -> list[SourceValidationResult]`
- Iterates all Source nodes
- Fetches each URL (with rate limiting: 1 request per second to be polite to kernel.org)
- Classifies content
- For stubs: extracts kernel-doc references, builds replacement URLs
- For directories: resolves to specific files
- Returns list of `SourceValidationResult(source_id, url, classification, word_count, kernel_doc_refs, suggested_replacement_urls, prose_excerpt)`

#### `generate_report(results: list[SourceValidationResult]) -> str`
- Produces a markdown report with:
  - Summary counts by classification
  - Table of all sources with classification, word count, and suggested replacements
  - List of sources needing manual review (classification = "thin")

## Phase 2: Source URL Remediation

### Task 2.1 — Spec DAG mutations

#### `INV-KK-EVIDENCE-EXCERPT-GROUNDED`
```
kind: invariant
id: INV-KK-EVIDENCE-EXCERPT-GROUNDED
language: meta
description: Evidence node excerpt text must be a summary derivable from the actual content of the linked Source document. The excerpt must not contain claims about topics, features, or APIs that do not appear in the source document. For sources pointing to code files, the excerpt summarizes the code's purpose and key API functions.
predicate: forall Evidence E with E.attrs.excerpt != null. forall claim C in E.excerpt. exists passage P in fetch(source_url(E)) such that C is derivable from P
predicateNL: Evidence excerpts only contain claims that are supported by the actual content of the linked source document.
enforced: {}
checked-at → stage-delivery
contained-by ← SUB-KK-INGEST
```

#### `INV-KK-CODE-EXAMPLE-SOURCE-VALID`
```
kind: invariant
id: INV-KK-CODE-EXAMPLE-SOURCE-VALID
language: meta
description: When a Concept code example has a source_url attribute, the referenced document must contain the API, function, or pattern that the code example demonstrates — either as documentation prose, function definition, or header declaration.
predicate: forall Concept C. forall example E in C.code_examples where E.source_url is set. fetch(E.source_url) contains reference to the primary API used in E.code
predicateNL: Code example source URLs point to documents that actually describe or define the demonstrated API.
enforced: {}
checked-at → stage-delivery
contained-by ← SUB-KK-INGEST
```

### Task 2.2 — Implementation: `scripts/remediate_sources.py`

Remediation script that:

1. **Loads the validation report** from Phase 1 (or runs validation inline)

2. **For each stub source** (classification = "stub"):
   - Takes the first kernel-doc reference as the replacement URL
   - Example: `slab.rst` references `mm/slub.c` → update Source URL to `https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/tree/mm/slub.c`
   - If multiple kernel-doc refs exist, pick the primary one (the `.c` file over `.h`, or the first listed)
   - Updates the Source node's `url` attribute in the database

3. **For each directory source** (classification = "directory"):
   - Fetches the directory listing
   - Identifies the most relevant specific document (prefer `index.rst`, then the largest `.rst` file, then the primary `.c` file)
   - Updates the Source node's `url` attribute
   - NOTE: Some directories (e.g., `Documentation/security`) cover multiple sub-topics. These may need to be split into multiple Source nodes, one per document. Flag these for manual review.

4. **For each code example with source_url pointing to a remediated source:**
   - Updates the `source_url` to match the new Source URL
   - Only updates if the old source_url matches the old Source URL

5. **Re-generates evidence excerpts** for remediated sources:
   - Fetches the new URL content
   - For code files (`.c`, `.h`): extract the file's header comment and function documentation comments as the excerpt (first 2000 chars)
   - For RST/HTML docs: extract the first 2000 chars of prose content as the excerpt
   - Updates the Evidence node's `excerpt` attribute
   - CRITICAL: Do NOT use model knowledge to generate excerpts. The excerpt must come from the fetched content only.

6. **Generates a remediation report:**
   - Sources updated: count and list
   - Code examples updated: count and list
   - Evidence excerpts regenerated: count and list
   - Sources flagged for manual review: count and list (directories with ambiguous best-file)

## Risk Notes

- **Rate limiting:** Fetching 47 URLs from kernel.org needs rate limiting (1 req/sec minimum). Total fetch time: ~1 minute.
- **Directory resolution ambiguity:** Some directory sources (e.g., `Documentation/security`) cover broad topics. The best replacement file may not be obvious. These should be flagged for manual review rather than auto-resolved.
- **Excerpt quality from code files:** When a source is a `.c` or `.h` file, the excerpt comes from file comments. If the file has minimal comments, the excerpt will be thin — but this accurately reflects the source content, which is the goal.
- **Kernel-doc rendering:** Some RST files are stubs that only make sense when rendered through the kernel's Sphinx build (which inlines the kernel-doc content). The rendered HTML on kernel.org/doc/html/ includes this content. For the 4 HTML sources we already have, the content is substantive because it's the rendered output. The git.kernel.org RST sources show the raw directives.
- **Existing spec invariants:** `INV-KK-EXTRACT-PROVENANCE` requires every Concept to trace to Evidence via `extracted-from`. This plan doesn't break that chain — it improves the quality of what's at the end of the chain (the Source URL and Evidence excerpt).

  ↑ sourced-from
